# 项目总控与启动门禁

## 一、项目结果

在不改变综合方案业务边界的前提下，交付福礼社单商户供应链平台五端系统：公司Admin后台、供应商后台、企业门户/企业采购、个人用户小程序、跑腿配送小程序，以及统一API、数据库、异步任务、审计和部署底座。

最终结果必须可由119项P0逐项证据证明；“代码已写完”不是结果，“可追溯、可验证、可恢复、经授权可上线”才是结果。

## 二、启动硬门禁

执行任何代码修改前，Codex必须完成并记录：

1. 读取综合方案、仓库根 `AGENTS.md`、`16-项目状态.json`、当前任务行和对应P0行。
2. 计算综合方案SHA-256，应为 `1153157234D2DCCDF38F0C5E468BD5D93889140153F1C21F7FEBB8FA5316EF92`；不同则暂停受影响任务并走基线变更流程。
3. 运行只读检查：`git status --short`、`git branch --show-current`、`git remote -v`、`git log -5 --oneline`、`node --version`、`pnpm --version`、`gh auth status`（若使用GitHub）。
4. 确认没有覆盖用户改动；不得用`git reset --hard`、盲目checkout或无审查的`git add -A`。
5. 当前阶段的前置 `M*-GATE` 必须有新鲜证据；否则只允许修复前一门禁。
6. 写明本任务目标、非目标、P0、依赖、文件范围、迁移/API/页面影响、失败测试和回滚。
7. 只有一个任务可处于`IN_PROGRESS`；并行任务必须使用独立worktree且不得碰同一文件或迁移链。

## 三、每个切片的固定执行序列

1. 读取当前代码与真实运行入口，确认基线而非猜测。
2. 更新字段字典、状态机、权限、页面/API/P0映射的待冻结项。
3. 先更新OpenAPI、Request/Response DTO白名单、错误码和幂等语义。
4. 编写失败测试：正常、越权、重复、并发、非法状态、失败恢复、历史快照、敏感字段泄露（按适用性）。
5. 运行失败测试并保存“预期失败且原因正确”的证据。
6. 实现最小纵向切片：migration→domain→API→UI，不混入后续阶段。
7. 运行focused tests；再运行适用的`pnpm verify`和迁移dry-run。
8. 检查diff、DTO字段、supplierId/用户/企业数据域、整数金额、事务、锁、幂等、日志脱敏和回滚。
9. 更新任务状态、P0证据、迁移/API台账和项目状态；创建/更新Draft PR。
10. 报告实际证据与未执行项。没有执行的真机、预发布、生产或人工合规必须写`NOT_EXECUTED`或`BLOCKED_EXTERNAL`。

## 四、固定质量命令

M0应在正式仓库建立统一命令：

```text
pnpm lint
pnpm typecheck
pnpm test
pnpm test:api
pnpm test:e2e:p0
pnpm prisma:validate
pnpm prisma:migrate:dry-run
pnpm openapi:generate
pnpm openapi:check
pnpm build
pnpm verify
```

阶段早期不存在的检查必须由M0按明确占位策略创建；不得用永远成功的空脚本冒充。命令失败时修根因，不删测试、不降断言、不跳过门禁。

## 五、交易和并发不变量

- 每个SKU只有一条`InventoryBalance`成交库存真源；个人与企业共用，预扣/释放/确认必须原子且幂等。
- 金额全部为整数分，客户端只提交选择和数量；售价/供应价/运费/优惠由服务端重算并在订单项留不可变快照。
- 同一`Idempotency-Key`只能产生同一业务结果；相同键不同请求体返回冲突，不得再次扣款/扣卡/扣库存/抢单。
- 微信通知必须验签、校验商户/应用/订单/金额并使用外部交易号唯一约束；未知结果先查询，禁止盲重试。
- 福利卡先冻结后确认；混合支付取消/失败必须补偿解冻；退款按`OrderPaymentAllocation`原结构拆分。
- 福利卡永久不提供个人现金充值；只允许企业发放、公司赠送、实体卡/卡密兑换三类受审计入账来源。
- 抢单使用数据库CAS/唯一约束；失败与超时返回可查询的未知结果，不允许两个跑腿员成功。
- 企业订单的类型守卫必须从领域层、数据库关系、API和测试四层阻止创建`DeliveryTask`。
- 发起人与复核人必须比较自然人身份`identityType + identityId`；跨职能账号不能规避同人复核禁令，超级管理员也不能替代独立复核人。
- 已确认账单、账本、价格历史、支付退款、物流节点和审批不得覆盖；错误使用追加调整/冲正。

## 六、门户缓存与契约生成边界

- 门户公开宣传、分类、商品列表和商品详情使用Next.js App Router的SSG/ISR，并具备可审计的按slug失效机制、robots与sitemap。
- 企业注册、登录、购物车、结算、订单和账户页面必须动态渲染，设置`noindex`且不得进入共享缓存；草稿、未发布和受限商品同样不得缓存或被搜索收录。
- `scripts/generate-openapi.ts`必须从NestJS应用确定性生成OpenAPI；`openapi-typescript`生成共享类型；Web使用`openapi-fetch`，两个原生小程序使用基于`wx.request`的共享适配器，禁止直接调用依赖浏览器Fetch语义的客户端。
- CI必须执行`pnpm openapi:generate`、`pnpm openapi:check`和生成物`git diff --exit-code`；破坏性契约变更由固定版本的`oasdiff`阻断。

## 七、供应价四层隔离

1. 数据权限：仅公司价格/财务和本供应商价格/财务账号可读。
2. 查询层：所有查询先绑定`companyId`或`supplierId`数据域。
3. DTO层：消费者、企业、门户、跑腿和其他职能的DTO无供应价字段。
4. 证据层：为每个公开/越权接口写响应白名单测试和日志/导出泄露测试。

前端隐藏列不是安全措施；数据库实体直接返回一律阻断。

## 八、阶段解锁规则

- 任务`DONE`：实现、契约、迁移、测试、证据、回滚均齐全，且无未解释FAIL。
- 阶段`GATE_PASSED`：该阶段所有任务DONE；必需CI是最新提交；P0达到要求证据或有经人工接受的外部阻塞；交接已归档。
- 下一阶段`READY`：只在上一阶段门禁通过并由授权人确认后更新。
- 技术可合并不等于已合并；已合并不等于已上线；已上线不等于生产验收通过。

## 九、基线变更流程

1. 保存当前哈希、差异和受影响任务/P0。
2. 只读确认变更来自用户批准的新方案，不自行决定业务口径。
3. 更新综合方案后，按顺序更新提示词包、执行包、字段/状态机/API、测试和已开Issue/PR。
4. 对已完成任务执行影响分析和回归；旧证据可能失效时降回`NOT_EXECUTED`。
5. 在变更日志和阶段交接中记录批准人、日期、原因、回滚方案。

## 十、人工保留事项

真实账号/实名、GitHub权限与Secrets、微信支付证书和真实资金、法务/税务/备案结论、真机正式验收、生产迁移、Release、部署和最终Go/No-Go均由授权人工完成。Codex可准备清单、Adapter、测试和证据模板，但不能伪造完成或替人批准。

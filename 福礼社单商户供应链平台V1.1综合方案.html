二、业务边界与核心红线

2.1 必须遵守的十四条红线

  1. 唯一销售主体：前台商品、订单、收款、退款、发票和用户协议均以江苏福礼团供应链科技有限公司为经营主体。
  2. 供应商不是店铺：供应商不拥有装修页、店铺首页、独立购物车、用户收款账户或面向用户的客服体系。
  3. 三类价格、分级审核：供应商价格职能页面自主设置供应价、平台零售价和集采销售价；首次上架时三类初始价格在公司价格审核独立页面审核，与公司商品页面的资料审核均通过后才上架。商品上架后，供应价变更必须提交公司价格审核页面，审核通过前继续使用原供应价；两类销售价变更不需要审核。
  4. 供应价严格保密：供应价是公司与对应供应商之间的内部采购及结算数据，仅公司价格审核/财务职能页面和该供应商价格/财务职能页面可见；个人用户端、企业采购端、门户公开页、跑腿端、其他职能页面、对客订单/发票/售后页面及其接口、导出文件均不得展示或返回供应价、供应价快照及可直接推算供应价的内部毛利字段。
  5. 结算不在线出款：系统负责核对、确认、差异处理和凭证留存，不自动向供应商提现或打款。
  6. 订单资金归公司：福利卡由公司统一发行和记账，用户微信支付进入公司收款渠道；供应商不得接触福利卡资金或诱导用户线下交易。
  7. 现金渠道只保留微信：P0 个人零售的现金应付只通过公司微信支付完成，可与福利卡混合；企业在线付款也只使用公司微信支付，对公转账属于独立的企业线下到账确认方式。本期不接入支付宝或其他现金支付渠道。
  8. 跨供应商统一对客：个人零售和企业采购均允许一个主订单包含多个供应商商品，客户只与公司统一结账；系统按供应商拆分履约、责任和应付，公司分别与供应商对账结算。
  9. 物流保持简单：不做自动派单、智能路线、多级配送网络或按地图实际里程结算；地图只提供“供应商取货点 → 用户收货目的地”两阶段设备导航。
  10. 商品分类驱动详情：每个商品必须绑定末级分类与分类模板，详情字段、资质、SKU 和前台模块按模板渲染。
  11. 企业采购不是团购活动：“社区集采”只作为门户企业采购入口名称，企业注册认证后可持续浏览和下单，不依赖社区、时间或成团条件。
  12. 商品资源共用：用户小程序和企业采购入口必须共用同一套 Product、Sku、分类模板、图片和库存；集采标识只决定渠道展示，不复制商品。
  13. 企业订单统一配送：企业采购主订单可以包含多个供应商商品，平台负责拆分备货、汇总和统一配送，任何企业采购配送任务都不得进入跑腿抢单大厅。
  14. 全过程可追溯：审核、价格、库存、订单、退款、对账、线下结算标记和物流节点均保留操作记录。

3.7 公司职能账号、权限模型与生命周期

  • 权限采用“固定职能账号类型 + 数据范围 + 字段权限 + 按钮权限”四层模型；一个职能账号只绑定一个 accountType 和一个固定 workspaceRoute，禁止把多个职能权限取并集后生成综合页面。
  • 同一自然人可通过同一登录身份持有多个职能账号，但每次会话只激活一个 functionalAccountId；切换时必须返回账号选择页，重新签发职能范围明确的会话。
  • 数据范围至少包括：全公司、指定供应商、指定商品分类、本人创建/分配工单；不能只靠前端筛选限制数据。
  • 供应价查看、供应价审批、退款复核、福利卡人工调整、线下付款登记、银行账户复核、敏感导出分别使用独立权限点，不打包成一个“财务管理”大权限。
  • 凡规则要求 maker-checker、申请/审核、制单/复核或独立审计时，服务端必须比较 FunctionalAccount.identityType + identityId；申请人和复核人不得是同一自然人，即使两次操作使用不同 functionalAccountId。冲突时操作保持待复核，不允许超级管理员绕过。
  • 创建职能账号 → 选择固定职能类型 → 邀请身份激活 → 配置数据/字段/按钮范围 → 正常使用 → 调岗新建或回收对应职能账号 → 锁定/离职禁用 → 会话失效 → 审计归档，全流程保留操作者和前后值。
  • 高风险临时权限必须设置到期时间，到期自动回收；系统不得删除全平台最后一个可用超级管理员职能账号。

小团队运营指引：上述 10 种公司职能类型定义的是权限隔离粒度上限，不等于最低人员配置要求。同一自然人可持有多个职能账号，登录后在账号选择页切换进入对应独立页面，每次会话仍只激活一个职能，服务端页面级隔离机制不受影响。3-5 人的初创团队可覆盖日常运营；推荐按“超级管理员兼门户内容、供应商运营兼订单客服、商品与分类运营兼福利卡运营、价格审核兼财务、物流兼审计只读”分配。该示例不是审批隔离豁免：任何人不得审核自己在另一职能账号发起的操作，审计人员不得独立关闭涉及本人操作的风险事项；人员不足时，高风险操作必须保持待第二自然人复核。

注册手机号 → 创建主体 → 填写企业与联系人 → 上传资质 → 填写供货及结算信息 → 提交审核 → 公司补正/通过/驳回 → 签署线下合同 → 激活后台

资料组必填内容审核要点
主体资料企业名称、统一社会信用代码、营业执照、注册地址、法定代表人。证照有效、名称一致、经营范围匹配。
业务资料供货分类、品牌授权、生产/经营许可、仓库或取货地址、联系人。分类资质、授权链、取货地可用。
结算资料收款单位、开户行、银行账号、税号、开票类型。收款单位原则上与合同主体一致，变更须复核。
履约资料备货时长、营业时间、退货地址、售后联系人。能否满足平台承诺、异常联系是否有效。

4.2 供应商状态

DRAFT 草稿 → PENDING_REVIEW 待审核 → NEEDS_REVISION 待补正 → ACTIVE 已启用 → SUSPENDED 已暂停 → TERMINATED 已终止

  • 暂停后不得提交新商品、接收新履约单；历史订单、售后和对账仍可访问。
  • 终止前必须处理未履约订单、售后差异、发票和未结算对账单。
  • 供应商按主体、商品、价格、库存、履约、售后、财务和审计分别创建职能账号与独立页面；银行账户和主体管理职能账号变更必须二次验证。

4.3 供应商各职能独立页面内容

供应商后台不是把下列模块组成一个综合菜单，而是按职能账号分别建设独立页面。共用组件可以复用代码，但页面路由、会话上下文、接口权限和数据请求必须以当前职能账号隔离。

独立页面硬边界：每个供应商职能账号只进入表中对应的一个页面，不出现其他职能菜单。同一员工兼任时，为其绑定多个职能账号；登录后在账号选择页分别进入，任何一次会话都只激活一个职能账号。

小团队运营指引：上述 8 种供应商职能类型同样不等于最低人员要求。小型供应商 1-2 人可通过一人多账号、切换进入的方式覆盖日常职能；页面级隔离和服务端权限校验不受兼任影响。银行账户、主体资料和其他要求双重确认的敏感变更仍按自然人身份执行职责分离，不允许同一人员切换账号自行复核；人员不足时由公司侧独立复核或保持待处理。随业务量增长再逐步拆分专人专岗。

4.8 商品管理总体设计：功能完整、操作收敛

商品管理设计结论：供应商商品运营账号只使用一个固定独立页面 /supplier/workspaces/products，页面内部包含商品工作台、商品列表、新建/编辑向导、批量任务、审核补正、版本记录和前台预览。完整能力集中在一个职能页面内，但不把价格、库存、履约和财务字段混进来。供应商日常操作收敛为“找到商品 → 看清当前状态 → 点击唯一下一步动作”；新商品支持快速新建、复制已有商品和模板导入三条路径。
设计原则具体做法明确禁止
一个页面完成商品资料工作商品工作台、列表、编辑、审核反馈和版本记录都在商品职能页面内部完成；列表进入详情或抽屉后可返回原筛选位置。不得为了填写价格、库存而把其他职能接口和字段加载进商品页面。
一个状态对应一个主动作草稿显示“继续完善”，待提交显示“提交审核”，待补正显示“立即补正”，审核中显示“查看进度”，已上架显示“查看/创建修改版本”。不同时展示多个含义接近的主按钮，不让供应商猜测下一步。
高频字段直接展示名称、分类、品牌、图片、SKU、渠道标识、备货信息和资质直接填写；低频扩展参数折叠在“更多信息”。不把所有分类的全部字段一次性铺满页面。
系统自动完成重复工作自动保存草稿、规格继承、SKU 矩阵生成、图片排序、分类模板带入、重复商品检测、字段完整度计算和审核意见定位。不要求供应商在多个页面重复填写相同品牌、单位、资质和履约信息。
前台结果可预见编辑过程中随时预览个人小程序和企业采购商品详情；只预览对客字段，不展示供应价和内部状态。不允许供应商提交后才发现图片裁切、规格名称或分类详情模块错误。

4.13 商品、价格与库存的跨职能交接

简单不等于越权：商品运营页面可以显示“价格是否就绪、库存是否就绪”的状态，但不能显示价格值或库存数量；需要其他职能处理时，只生成待办和受控账号切换提示，不直接打开其他职能页面或复用当前会话。

发布条件商品运营页面展示由谁处理完成后结果
商品资料未完善、可提交、审核中、待补正、已通过。供应商商品运营账号提交，公司商品与分类运营账号审核。资料通过后形成不可覆盖的审核版本。
初始价格未提交、审核中、待补正、已通过；只显示状态，不显示金额。供应商价格管理账号填写三类初始价格，公司价格审核账号审核。初始价格通过并形成首个价格版本。
库存准备未维护、库存不足、可售；只显示状态，不显示数量。供应商库存/仓库账号通过库存接口维护对应 Sku 的唯一 InventoryBalance。至少一个启用 SKU 满足可售库存条件；个人与企业渠道读取同一库存真值。
上架就绪以“资料、价格、库存”三项进度显示 0/3 至 3/3；主动作根据当前缺口变化。各职能分别处理，公司在规则满足后发布。Product/Sku 进入 ACTIVE，并按个人销售开关和集采标识进入对应货架。
  • 商品资料提交后，系统自动向价格管理账号发送“初始价格待提交”待办；商品账号只看到已通知，不看到价格页面数据。
  • 公司退回商品资料时，审核意见必须关联步骤和字段；供应商点击“立即补正”直接定位首个问题，逐项处理后重新提交。
  • 同一员工兼任商品、价格或库存职能时，点击“切换职能处理”必须返回账号选择页并重新签发单职能会话。
  • 上架条件不满足时展示缺口和责任职能，不使用“未知错误”或要求供应商自行联系客服排查。

4.14 上架后编辑、上下架与版本管理

操作处理规则页面反馈
修改一般展示资料对允许即时修改的非关键字段保存新版本并留痕；公司可配置需要复核的字段范围。明确显示“保存后立即更新”或“提交后审核”，不能同一按钮混用两种后果。
修改关键资料分类、品牌、SKU 结构、资质、重要参数、警示语和售后规则等创建待审核新版本；原线上版本继续服务已有交易。编辑页同时显示“线上版本”和“待审核版本”，支持差异对比、撤回和审核意见定位。

停用 SKU无新订单可售；已被订单引用的 SKU 保留历史快照和履约能力，不能物理删除。确认框列出受影响渠道、购物车和未完成订单处理规则。

公司强制下架立即停止新交易并记录原因；供应商只能查看、补正和申诉，不能自行恢复。列表置顶风险条，明确影响渠道、原因、补正材料和申诉入口。
归档草稿只有未提交、未上架且无订单/审核引用的草稿可归档；归档后可恢复。默认使用可恢复归档，不提供高频物理删除按钮。

4.15 让复杂功能保持简单的交互规则

  • 一屏一个目标：列表用于找商品和处理待办，向导用于填资料，详情用于看状态和记录；不在同一屏堆叠所有功能。
  • 一个主按钮：每个状态只有一个推荐动作，次要动作降级为文字按钮或“更多”。
  • 按需展开：先展示分类必填与高频字段，低频信息、内部备注和高级包装参数折叠；字段依赖条件满足后再出现。
  • 自动带入：品牌、单位、取货地址、售后模板、备货时长和常用资质可以从主体默认或最近商品带入，并清楚标记来源。
  • 就地纠错：字段下方直接说明错误和修复方法；提交检查页可点击错误跳转，不使用只列错误代码的弹窗。
  • 不中断工作：自动保存、断网草稿、本地未提交提示、离开保护和网络恢复后重试；重复提交不生成重复审核单。
  • 预览一致：个人端和企业端预览使用正式渲染组件与当前模板版本，不制作另一套容易失真的静态预览。
  • 帮助贴近操作：字段旁显示示例和规则，复杂分类提供“查看填写示例”；帮助不遮挡当前编辑内容。
  • 敏感数据不预取：商品页面的价格/库存就绪状态由专用汇总 DTO 返回，不通过隐藏列、前端过滤或下载接口携带实际值。

  3. 商品主要字段组均由分类模板控制必填、类型、单位、枚举、依赖和前台详情模块，不允许前端硬编码一套通用表单。
  4. 快速新建、复制商品和模板导入三种路径均可生成草稿，复制不携带价格、库存、审核和订单数据。

五、商品分类与分类模板

5.1 分类治理原则

  • 采用“一级分类 → 二级分类 → 末级分类”树；商品必须绑定一个可用末级分类。
  • 末级分类绑定唯一启用的 CategoryTemplate 版本，决定必填字段、SKU 维度、详情模块、资质和售后提示。
  • 分类名称用于导航，模板用于数据治理；不能只创建分类而没有模板。
  • 模板变更使用版本号，已上架商品不被静默覆盖；必要时生成补录任务。

六、商品模型、审核与生命周期

6.1 两层商品模型

对象归属内容是否可售

InventoryBalance公司共用库存域每个 Sku 一条库存真源，记录可用、冻结/预扣、已售数量和乐观锁版本；个人与企业订单共同使用。自身不是商品；只有 ACTIVE Sku 且可用库存大于零时可成交。

6.2 商品审核流程

供应商商品页面提交商品资料 → 供应商价格页面提交三类初始价格 → 系统分别生成资料审核与初始价格审核 → 公司商品页面审核图文/分类/SKU 属性/资质 → 公司价格页面审核初始价格 → 两项均通过后上架；上架后供应价变更进入价格审核页面，两类销售价可在供应商价格页面直接调整

  • 供应商商品职能页面维护商品资料但不显示价格；供应商价格职能页面维护三类初始价格。首次上架时分别形成商品资料审核单和初始价格审核单，二者均通过后才能上架。
  • 商品上架后，供应商修改供应价必须生成 SupplyPriceChangeRequest 并提交公司审核；审核通过前原供应价继续有效，审核通过后立即或按批准的生效时间用于新订单，历史订单仍使用原供应价快照。
  • 商品上架后，供应商修改平台零售价或集采销售价不需要公司审核；保存后立即生效或按供应商设置的未来生效时间自动生效，仅影响生效后的新订单并写入价格变更日志。
  • 供应商发布商品时必须明确是否勾选“集采标识”；集采标识启用、商品为 ACTIVE、集采销售价有效且库存可用时，商品自动进入门户企业采购货架。
  • 关闭集采标识后商品立即停止接受新的企业采购订单，但不影响个人小程序展示，也不影响已有企业订单、售后和供应商对账。
  • 平台零售价和集采销售价直接调价时，系统校验金额格式、非负值、价格关系和异常幅度并生成价格变更日志；异常提醒不转化为审批。供应价则必须走审核状态机。
  • 分类、资质、商品关键参数和售后规则等非价格字段发生重大变化时仍须重新审核，审核前继续使用原线上版本。
  • 公司不能不经供应商提交直接替换三类价格；公司对供应价变更作通过或驳回决定，对平台零售价和集采销售价只做异常监控，不把监控变成审批。
  • 公司发起平台活动时可以提出活动价方案，供应商确认后按活动生效时间上线。
  • 公司可以暂停或强制下架，并必须填写原因；供应商可查看原因但不能自行恢复。
  • SKU 已被订单引用后不物理删除，只能设为不可供货或不可售。

9.5 福利卡与微信支付混合流程

跨供应商提交一个个人主订单 → 校验全部商品/供应商/库存/配送范围 → 锁定三类价格快照并按供应商拆分履约子单 → 预扣库存 → 选择福利卡账户 → 冻结福利卡额度 → 计算微信支付应付（cashAmount）→ 福利卡全额支付或调起公司微信支付 → 向公司完成一次支付 → 服务端查单/验签确认 → 通知各供应商分别备货

福利卡全额支付cashAmount = 0，不调外部支付；在同一幂等事务中将福利卡冻结转实扣、订单置为 PAID 并写流水。
福利卡＋微信支付先冻结福利卡额度，再为微信支付差额创建 PaymentTransaction；微信支付成功后，福利卡冻结转实扣并完成订单。
用户主动取消前端上报取消意图，后端先查询微信支付交易；确认未支付后释放福利卡冻结、优惠券和预扣库存。
支付失败/超时微信支付状态确认失败或关闭后解冻福利卡；状态未知时先保持冻结，由微信查单和补偿任务处理，不能误释放已支付订单。
  • 订单创建、福利卡冻结、福利卡实扣、福利卡释放、微信支付回调和订单置为已支付均有独立且唯一的幂等键。
  • 重复点击、重复回调或补偿重试不得重复扣福利卡、重复收现金、重复扣库存，也不得为个人供应商履约子单重复生成 DeliveryTask，或为企业主订单重复生成 EnterpriseDeliveryOrder。
  • 福利卡账户余额不足、被冻结或适用范围变化时，结算页必须重新计算并让用户确认现金差额。

9.6 拆分退款与资金回退

  • 创建订单时把福利卡和现金金额按商品实际可付金额分摊到 OrderPaymentAllocation，并保存到每个订单项；尾差使用确定性规则落到最后一个可抵扣商品。
  • 全额退款：福利卡实扣部分退回原福利卡账户，微信支付实付部分退回原微信支付交易。
  • 部分退款：严格按被退款订单项保存的福利卡/微信支付分摊快照退回，不按退款时余额或当前商品价格重新计算。
  • 退款中的福利卡金额写入 WelfareCardLedger 的 REFUND 流水；微信支付退款写入 PaymentTransaction/RefundTransaction。
  • 原福利卡账户被冻结、停用或规则发生变化时，退款金额仍进入原账户的退款待处理状态，由财务/客服按批准规则处理，不得直接丢弃或改退到其他用户。
  • 供应商只参与售后责任判断；用户使用福利卡还是现金，不改变供应商订单供应价快照和应付货款计算。

9.7 福利卡账务与公司财务对账

账务对象要求
WelfareCardLedger发行、领取、冻结、解冻、实扣、退款、冲正、人工调整全部只追加流水，不覆盖历史记录。
账户余额可用余额、冻结余额与流水汇总必须一致；任何时点不得出现负余额。
企业资金企业采购金额、已发放、未领取、用户余额、已核销、已退款和剩余责任可按批次核对。
混合支付每日核对订单福利卡实扣、微信支付实付、订单总额、退款拆分和微信支付账单。
人工调整仅限授权财务人员，必须 maker-checker 双人复核、填写原因并生成 ADJUSTMENT/REVERSAL 流水。
供应商结算隔离供应商对账只依据履约数量、供应价快照、退款责任和调整项，不按福利卡/微信支付比例分摊。

9.8 福利卡合规上线门槛

福利卡仅通过企业福利发放、公司活动赠送和实体卡/兑换码三种方式取得额度，不提供个人现金充值功能。发行、备案、章程协议、退款和信息公示等要求应在上线前由公司法务、财务及主管部门结合实际发行模式确认。
  • 公司应在上线前依据商务主管部门现行规则确认发行主体、适用范围、备案和预收资金管理要求。
  • 系统支持实名登记、企业批次资金来源、协议版本和公示内容字段，但具体阈值不在代码中写死。
  • 福利卡章程、用户协议、退款说明、客服渠道和隐私说明必须在发行、领取、绑定和支付前可查看。
  • 参考依据：商务部《单用途商业预付卡管理办法（试行）》及江苏省商务厅单用途商业预付卡公告公示要求；正式上线以届时有效规定和主管部门意见为准。

库存含义

平台可售库存公司根据可供库存、安全库存、活动锁定和风控计算的对外销售数量。

9.10 订单通用要求

  • 个人和企业主订单均可包含多个供应商订单项；订单内部保存商品标题、SKU、平台零售价/集采销售价、经审核生效的供应价、供应商、分类模板版本、配送费、福利卡计划/账户、福利卡抵扣、微信支付实付（账务字段 cashAmount）和售后规则快照。供应价快照属于内部结算字段，必须从所有个人端、企业端和跑腿端响应 DTO 中剔除。
  • 支付回调必须验签、幂等；重复回调不得重复扣福利卡、现金、库存、生成个人或企业配送单或记账。
  • 退款由公司发起并按原支付结构退回用户；供应商只参与责任确认，不直接向用户退款。

十、配送端：个人跑腿与企业统一配送完整方案

配送端由两套严格隔离的履约体系组成：个人零售订单按供应商履约子单生成跑腿任务，进入独立跑腿小程序抢单大厅；企业采购订单先汇总各供应商货物，再由公司物流职能页面安排公司车辆、司机或指定承运商统一配送。企业配送任务绝不进入跑腿大厅，跑腿员也绝不访问企业配送数据。

10.1 双配送链路与系统边界

项目个人零售跑腿企业采购统一配送
订单来源用户小程序个人零售主订单。门户社区集采企业采购主订单。
拆分方式主订单按 supplierId 生成多个 SupplierFulfillmentSubOrder；每个个人子单可生成一个 DeliveryTask。主订单按 supplierId 生成多个备货子单，全部或按公司确认方案汇总到一个 EnterpriseDeliveryOrder。
执行入口独立跑腿小程序：注册/登录、上线、抢单、节点、导航、异常、记录。公司物流职能账号固定独立页面：汇总收货、派车/承运、移动执行、签收和异常。
执行人员经公司审核启用的跑腿员。公司物流职能人员、公司指定司机或第三方承运商；P0 不为第三方承运商开放平台后台账号。

导航任务必须同时保存供应商取货点和用户收货目的地；抢单后至取货前导航到取货点，确认取货后自动把当前导航目标切换为收货目的地。公司物流执行页可把平台汇总点和企业目的地分别传给执行人员本人手机地图，仅用于相应阶段导航。
明确隔离不查看企业订单、企业地址、企业发票或企业配送单。不生成 DeliveryTask、不进入抢单大厅、不使用跑腿账号或跑腿报酬。

10.2 任务生成、投放与主订单关系

个人主订单支付成功 → 按 supplierId 幂等生成个人履约子单 → 幂等创建 DeliveryTask → 供应商确认可取货 → 任务进入 PENDING_HALL → 合格且在线跑腿员可见 → 抢单成功 → 取货/配送/送达 → 用户订单按多个子单汇总总进度

  • 一个个人 SupplierFulfillmentSubOrder 只能关联一个有效 DeliveryTask；网络重试、重复回调或补偿任务不得重复创建。
  • 任务在订单已支付、子单有效且供应商确认可取后进入抢单大厅；未备货、取消、退款锁定或风控冻结的任务不可抢。
  • 一个个人主订单包含多个供应商时，分别产生多个任务；这些任务可以由不同跑腿员承接、在不同时间取货和分批送达。
  • 用户端仍只显示一个公司主订单和一次支付，配送详情按供应来源子单展开；用户不向跑腿员或供应商再次付款。
  • 企业采购子单即使已备货也只能进入企业汇总收货流程，任务生成服务必须在服务端以 channelType 拒绝为其创建 DeliveryTask。

10.7 抢单并发、幂等与失败反馈

  • 客户端先显示提交中并禁用按钮，收到明确成功后进入任务详情；网络未知时先查询“我的任务”，不能直接再次抢单。
  • 任务已被抢、已取消、区域不匹配、账号下线、在途超限和会话失效使用不同用户可读错误码。
  • 抢单前后数据使用不同 DTO：大厅摘要不含精确隐私，承接成功后任务详情才返回履约所需字段。

  • 任何扣减不得直接改历史订单或已确认账单，应新增调整项。

十二、线上对账与线下结算

12.1 对账原则

系统不建设供应商钱包、余额提现和自动分账。系统只计算“公司应付供应商多少”、支持双方线上确认与差异处理；实际付款在线下完成，付款后由公司财务登记流水号并上传凭证。用户使用纯福利卡、纯微信支付或福利卡＋微信支付，都不改变经审核生效的供应价和应付货款口径。

12.2 对账单组成

项目计算口径
应付供应货款账期内已达到可结算状态的商品数量 × 订单供应价快照。
个人/企业多供应商订单按 SupplierFulfillmentSubOrder 将一个个人或企业主订单分别拆入各供应商账单；每个供应商只核对自己的商品、数量、经审核生效的供应价快照和责任调整。
退款/退货扣减已确认由供应商承担且应从应付款扣除的金额。
补发和质量赔付按公司与供应商合同及责任单形成调整项。
采购方支付结构个人福利卡/微信支付结构及企业微信支付/对公转账由公司财务单独核对，不进入供应商供货款计算，也不向供应商披露用户福利卡余额。
其他调整经双方确认的补款、扣款、税差和上期差异。
本期应付应付供应货款 − 扣减 + 补款；不包含平台零售价或集采销售价中的公司毛利。

→ PENDING_SUPPLIER_CONFIRM 待供应商确认
→ DISPUTED 有差异
→ PENDING_COMPANY_REVIEW 待公司复核
→ CONFIRMED 双方已确认
→ PENDING_OFFLINE_PAYMENT 待线下付款

→ ARCHIVED 已归档
  • 供应商可逐项查看订单、SKU、供应价快照、数量、退款和调整原因。
  • 差异申诉必须填写原因并上传凭证；解决过程留痕。
  • 公司财务登记付款日期、付款金额、银行流水号和凭证；供应商可在线确认已收款。
  • 已确认账单不得覆盖修改；发现错误时创建补充账单或冲正调整。
  • 供应商发票状态独立管理，不允许因为发票问题回写订单履约状态。

13.1 关键约束与索引

  • Supplier.companyId 必须指向唯一经营公司；所有供应商接口强制校验 supplierId。
  • PortalContent.slug 在公开内容中唯一；已发布内容必须指向不可变的 PortalContentRevision，修改后先生成新版本，不能覆盖历史发布快照。
  • 门户 CMS 只能维护宣传、新闻、案例、帮助和法律内容；企业商品、价格、库存、采购车和订单必须实时引用交易域对象，禁止复制为门户内容字段。
  • BusinessInquiry 联系方式加密存储并按用途授权；重复提交使用幂等键，统计与日志不得记录完整手机号或需求中的敏感信息。
  • ConsumerWechatIdentity 的 openId/unionId 只能用于服务端身份绑定并安全保存；前端不得传入任意 consumerUserId 访问个人数据，个人会话注销、停用或安全重置后必须撤销。
  • ConsumerAddress、ConsumerInvoiceProfile、ShoppingCart、ConsumerMessage、个人订单、福利卡和售后查询全部强制校验当前 consumerUserId；分享参数、页面路径和请求体均不能覆盖数据归属。
  • 同一购物车中的有效 ShoppingCartItem 以购物车、SKU 和业务状态保持确定性；提交订单时重新校验 Product/Sku、平台零售价、共用库存、区域、限购、福利卡范围和配送规则，不能使用前端缓存直接成交。
  • 个人小程序响应 DTO 只包含平台零售价和必要的供应来源展示字段，禁止返回集采销售价、供应价、供应价快照、供应商应付、跑腿报酬和内部毛利。
  • CompanyUser 不允许自助注册；SupplierUser.supplierId 由激活邀请在服务端写入，登录请求和前端路由不得传入或覆盖账号归属主体。
  • ApprovalTask.applicantId 与 reviewedBy 记录自然人身份主键；具体操作职能账号另写入审计上下文。要求双人复核时，两者必须不同，不能只校验两个 functionalAccountId 不同。
  • 每个 FunctionalAccount 必须且只能关联一个 FunctionalAccountType 和一个固定 workspaceRoute；公司与供应商账号类型使用不同 ownerType，任何会话不得同时激活多个职能账号。
  • 内部菜单、按钮、数据范围和字段权限必须以当前 functionalAccountId 由服务端统一计算；手工访问其他职能路由、复用其他页面接口或篡改账号类型均返回无权限。
  • 账号停用、锁定、离职或职能账号回收时，相关 AuthSession 必须立即撤销；限时职能账号以 FunctionalAccount.expiresAt 为准自动失效。
  • Product 必须保留 supplierId 和 supplierProductId，但销售归属为公司；个人与企业渠道引用同一 Product/Sku。
  • SupplierProductSku.requested* 只表示供应商提交值；成交和对账分别以 Sku.currentRetailSalePrice/currentEnterpriseSalePrice、Sku.approvedSupplyPrice 的生效版本为准，禁止从供应商草稿直接下单。
  • 每个 Sku 必须且只能有一条 InventoryBalance；个人和企业订单使用同一行乐观锁预扣与释放。商品表、供应商草稿、页面缓存和搜索索引不得保存可独立成交的第二套库存真值。
  • 个人零售和企业采购均使用公司主订单；主订单允许多个供应商订单项，不以单个 supplierId 表示归属，并按 orderId + supplierId 唯一生成 SupplierFulfillmentSubOrder。
  • 个人供应商履约子单可以且只能生成一个 DeliveryTask；企业供应商履约子单不得生成 DeliveryTask，只能汇总进入 EnterpriseDeliveryOrder。
  • 个人 DeliveryTask 进入 PENDING_HALL 前必须同时固化 pickupPointSnapshot 和 destinationSnapshot；取货点来自对应供应商履约子单，目的地来自个人订单地址快照，任一缺失均不得投放大厅。
  • RunnerSession.runnerId 由审核通过的跑腿账号在服务端绑定；跑腿端请求不得传入或覆盖 runnerId。跑腿账号暂停、冻结、停用或会话撤销后立即下线并禁止新抢单。
  • 抢单必须以 DeliveryTask.version 乐观锁完成 PENDING_HALL → ACCEPTED 与 runnerId 绑定；同一任务只能有一个当前承接人，重复请求幂等，转派必须追加 DeliveryTaskAssignmentLog。
  • 跑腿员只可访问大厅脱敏摘要和本人已承接任务；精确取送地址、受控联系方式和商品摘要仅在必要履约阶段返回，企业配送、价格、支付、福利卡和结算字段一律禁止。
  • DeliveryNodeLog 按任务、节点和幂等键防重复；服务端校验当前 runnerId 及合法前置状态，导航调用、客户端定位或前端按钮显示均不能替代节点状态变更。
  • DeliveryException、DeliveryProof、DeliveryTaskAssignmentLog 和 RunnerCompensationRecord 只追加或追加冲正，不覆盖原记录；跑腿员不能自行取消订单、删除任务、修改退款或私下转派。
  • 企业采购货架查询必须同时满足 saleStatus=ACTIVE、isEnterpriseProcurementEnabled=true、集采销售价有效和共用库存可用。
  • 企业采购订单不得生成 DeliveryTask；只能生成 EnterpriseDeliveryOrder，并由公司物流职能账号固定独立页面操作。配送项必须回指原订单项和供应商子单，派车资源保存快照。
  • 设备导航正式配置保持 MAP_PROVIDER=disabled 且禁止 MAP_PROVIDER_KEY；系统不调用服务端地图路线/距离接口，不以导航、定位、距离、拥堵或轨迹自动推进节点或计算费用。
  • 供应价变更必须存在审核通过的 SupplyPriceChangeRequest 才能更新 Sku.approvedSupplyPrice；平台零售价和集采销售价变更不得创建价格审批任务，但必须写入 PriceChangeLog。
  • Sku.approvedSupplyPrice、OrderItem.supplyPriceSnapshot、供应商应付金额和内部毛利只能出现在公司价格审核/财务职能接口及对应供应商价格/财务职能接口；其他职能、公共、个人、企业采购和跑腿响应模型必须使用独立 DTO 白名单，禁止直接序列化数据库实体。
  • P0 的 PaymentTransaction.channel 固定为 WECHAT_PAY；outTradeNo 全局唯一，服务端必须验签并核对商户号、订单号和金额后才能确认支付。前端成功回调不能直接改订单状态，其他支付 channel 值在本期必须被拒绝。
  • 微信支付回调、订单创建、福利卡冻结/实扣/解冻、退款、库存操作、对账生成均有唯一幂等键。
  • WelfareCardAccount.consumerUserId 必须属于当前用户；结算不能使用他人账户或不可用计划。
  • 福利卡可用余额和冻结余额必须与 WelfareCardLedger 汇总一致，且任何时点不得为负数。
  • 审核记录、价格变更、福利卡流水、库存流水、物流节点、账单调整和线下付款记录只追加，不物理删除。

十四、安全、合规与审计

14.1 认证与数据权限

  • 公司后台和供应商后台使用独立职能账号、独立页面和单职能会话；服务端每次请求都校验 functionalAccountId、固定页面、权限和数据归属，不能依赖前端隐藏。
  • 供应商职能账号只能访问本供应商且属于固定职能页面的数据：商品、价格、库存、履约、售后、财务和账号管理之间默认互不可见；不得通过主订单、路由或接口访问其他职能页面或其他供应商信息。
  • 跑腿员只能访问个人零售抢单大厅的脱敏摘要和本人已抢任务；企业采购订单和企业配送单对跑腿角色必须返回无权限。
  • 供应价采用字段级权限：公司价格审核和财务职能页面、对应供应商价格和财务职能页面可见；个人用户、企业客户、公众、跑腿员、其他职能页面以及其他供应商一律无权访问。
  • 用户端和企业端接口必须通过显式响应 DTO 返回平台零售价或集采销售价，响应体中不得出现 supplyPrice、approvedSupplyPrice、supplyPriceSnapshot、供应商应付金额、毛利或采购成本等字段。
  • 用户只能查看和使用绑定到本人账号的福利卡账户；卡密只保存加盐安全摘要，日志不得记录完整卡密。
  • 银行账户变更、福利卡人工调账、福利卡批量作废、线下付款标记、退款、强制下架、强监管放行需要二次验证和审计。

14.2 商品与内容合规

  • 食品、化妆品、图书、医疗器械、保健食品等按分类模板要求资质和页面警示。
  • 处方药、特殊管理药品和公司当前资质不支持的品类默认禁止发布或交易。
  • 商品富文本过滤脚本、事件属性和外部危险链接；图片、证照和结算凭证使用受控对象存储。

15.5 OpenAPI 契约双向约束

  1. 后端确定性生成 spec（禁止手写 YAML）：NestJS Controller 和 DTO 使用 @nestjs/swagger 装饰器。独立脚本 scripts/generate-openapi.ts 在关闭真实支付、短信、对象存储等外部副作用的生成模式下创建应用上下文，调用 SwaggerModule.createDocument()，按稳定键序列化并写入 packages/contracts/openapi.json；启动服务只负责按配置暴露文档，不作为提交文件的唯一生成方式。
  2. 类型与传输分层：openapi-typescript 从 openapi.json 生成 packages/contracts/types.ts。公司后台、供应商后台和企业门户使用 openapi-fetch 基于该类型创建客户端；原生用户/跑腿小程序复用同一生成类型，通过 packages/miniapp-kit 内唯一的 wx.request 兼容适配器发送请求。业务页面不得自行封装临时 fetch、axios 或 wx.request 客户端。
  3. CI 双向校验：后端 spec 变更后 CI 自动执行 pnpm openapi:check，该命令依次完成：
    • 运行 pnpm openapi:generate 导出最新 openapi.json，与仓库已提交文件比对；存在未提交差异则失败。
    • 用最新 spec 重新生成 types.ts，与仓库已提交版本比对；存在未提交差异则失败。
    • 运行 tsc --noEmit——前端代码引用了已删除或类型变更的字段时，TypeScript 编译报错，构建失败。
  4. 供应价字段契约锁定：spec 生成时通过 @ApiResponse 的 type 指定各接口返回的 DTO；对客端 DTO（如 ProductDetailDTO、OrderDetailDTO）不包含 supplyPrice、approvedSupplyPrice、supplyPriceSnapshot、供应商应付及毛利字段。CI 中运行契约测试（Supertest），以非授权职能账号调用全部对客接口，断言响应 JSON 中不存在上述字段。
  5. 破坏性变更检测：CI 锁定 oasdiff 明确版本，以目标分支已提交的 openapi.json 为基线对比当前 spec；检测到 breaking 级别变更即失败并输出报告。确需变更时必须先提供版本化路径、兼容期和迁移方案，不能通过删除检查或临时忽略规则放行。

15.6 企业门户渲染、缓存与 SEO 约定

  • 公开内容区：首页、关于、供应链能力、案例、新闻、福利卡服务、供应商合作、联系和协议政策使用 Next.js 静态生成或 ISR；CMS 发布/下线后按内容 slug 触发受鉴权的按需失效，页面源代码必须包含可抓取正文。
  • 企业交易区：注册认证、采购货架、企业商品详情、采购车、结算、工作台、订单、售后、资料和消息按实时性与身份使用动态渲染或客户端查询；用户特定响应必须 private/no-store，不得进入 CDN 公共缓存。
  • 索引边界：公开页生成唯一 title、description、canonical、Open Graph、结构化数据和 sitemap；登录、认证、采购车、结算、工作台、订单、售后及预览页统一 noindex,nofollow，并在 robots 规则中禁止抓取。
  • 验收：同时检查服务端 HTML、响应缓存头、sitemap/robots、内容发布失效和登录数据隔离；不能只用浏览器运行后的 DOM 或字符串锚点代替 SEO 与缓存证据。
